# RAG, Chat, and Latency Feature Writeup

## Page 1: How We Built the Psychologist-Style Chat Experience

Psych-Platform-Core was built as more than a normal chatbot. The goal was to create a backend that can respond like a careful psychologist-style support assistant: it listens first, detects emotional risk, retrieves relevant clinical guidance, remembers the conversation, and avoids unsafe generation during crisis situations. The system does not claim to replace a licensed psychologist. Instead, it behaves like a responsible mental health support layer that can power chat, voice, and future avatar clients.

The core chat experience starts at the FastAPI `/api/v1/chat` endpoint. When a user sends a message, the backend first stores the user message in PostgreSQL through the `ChatMessage` table. It then prepares a LangGraph state containing the user message, user id, session id, optional audio/video features, and any available long-term session summary. This state is passed into the LangGraph workflow with `thread_id=session_id`, which lets the graph keep the right conversation state for each session.

The LangGraph workflow is the main reason the system behaves more like a therapeutic conversation engine than a one-shot prompt. The graph begins with `SentimentNode`, which analyzes the user's current emotional state and assigns a risk score from 0 to 10. The sentiment step can also include multimodal hints such as voice tone, speech rate, vocal energy, facial emotion, gaze avoidance, and facial action units. This gives the model more context than plain text when voice or video clients are connected.

After sentiment analysis, the graph routes the conversation based on risk. If the risk score is 8 or higher, the graph marks the message as crisis-level and sends it to the crisis protocol. The crisis response is deterministic, not generated freely by the LLM. This is intentional. In a high-risk situation such as self-harm or suicidal intent, the system must not invent advice, minimize the danger, or hallucinate emergency guidance. The crisis node returns a fixed safety message that urges the user to contact local emergency services or a suicide prevention hotline immediately.

If the message is not crisis-level, the graph sends the state to `TherapyNode`. This node is responsible for producing the psychologist-style response. It uses the conversation history, detected mood, optional longitudinal memory, and retrieved clinical evidence. The response prompt asks the assistant to reflect the user's feeling first, validate the experience, avoid diagnosis, avoid rushing into advice, use simple conversational language, provide at most one small coping step, and ask exactly one gentle open-ended question. This prompt design is what gives the chat its therapeutic pacing: the assistant does not immediately jump into solutions, but first mirrors the emotion and helps the user feel understood.

The RAG feature is the evidence layer behind the therapy response. Instead of asking the LLM to answer only from its general training, the system retrieves relevant passages from the local clinical knowledge base. The knowledge base is built from mental health guidelines, instruments, and counseling datasets stored under the project data folders. Embeddings are generated with `BAAI/bge-base-en-v1.5`, and retrieval can run against Pinecone for cloud deployment or Qdrant for local development. This dual backend design lets the same application work both in a production-like cloud setup and in a free local setup.

The retrieval pipeline is tuned for precision. First, the system checks whether RAG is actually needed. Very short and neutral messages such as greetings can skip RAG, because retrieving clinical documents for every tiny message adds latency and can make the response feel unnatural. For clinically meaningful moods such as anxious, depressed, lonely, angry, stressed, fearful, hopeless, guilty, or confused, RAG is enabled even when the message is short.

When RAG is needed, the system expands the query using mood-specific clinical terms. For example, an anxious message is expanded with terms related to anxiety, CBT, exposure therapy, cognitive restructuring, and panic disorder. A depressed message is expanded with terms related to depression, behavioral activation, negative cognition, and mood disorder. This helps the vector search find passages that match not only the user's exact words but also the clinical concepts behind the concern.

The service then performs two Maximal Marginal Relevance searches in parallel: one with the raw user message and one with the mood-expanded query. MMR is used because it balances relevance and diversity, reducing the chance that the context block contains three near-identical chunks. The returned documents are merged, deduplicated by normalized content, and filtered for low-signal chunks such as very short fragments, noisy OCR, forms, copyright text, and sparse questionnaire fragments.

After filtering, the system scores candidate documents using a hybrid method. Lexical overlap checks whether the user's concrete terms appear in the document. Topic bonuses give a small boost when document metadata matches the detected mood, such as anxiety, stress, depression, relationship, or crisis. An optional cross-encoder reranker can be enabled with `ENABLE_RERANKER=true`, but it is off by default because CPU reranking can add 1 to 3 seconds per request. The default path favors fast MMR plus lightweight scoring, which is enough for the current knowledge base size and the target latency budget.

The final selected context is kept small: up to three high-value documents are rendered into the prompt, with source and page metadata when available. This matters because a psychologist-style answer should be grounded without becoming overloaded. Too much retrieved text can cause the LLM to sound like a textbook. A concise context block keeps the response natural while still anchoring it in clinical evidence.

## Page 2: Memory, Streaming, and Latency Work

The chat feature also includes memory at two levels. First, every user and assistant message is persisted in PostgreSQL so the application can keep an auditable session history. Second, LangGraph uses a persistent checkpointer. In production, PostgreSQL checkpointing is used; in local development, SQLite checkpointing is supported. This means multi-turn graph state can survive beyond a single in-memory request. The system also includes a `SummaryNode` that can compress session history every configured interval and save a session summary. Later turns can load recent past-session summaries as longitudinal context, helping the assistant notice recurring patterns instead of treating every message as a completely new conversation.

This long-term context is merged carefully. If both previous-session memory and clinical RAG evidence exist, the therapy node separates them into `[Previous sessions]` and `[Clinical evidence]` sections. If only previous-session memory exists, it still gives the LLM continuity. This design supports a more psychologist-like flow: the assistant can remember that a user has repeatedly mentioned loneliness, work stress, anxiety, or sleep problems, while still keeping the current response grounded in clinical material.

The backend supports three response modes. The first is the standard blocking `/chat` endpoint, which waits for the full graph result and returns a single JSON response with `response`, `detected_mood`, and `risk_level`. This is useful for normal web or mobile chat. The second is `/chat/stream`, which returns Server-Sent Events with a metadata event followed by token events and a final done event. This is useful for clients that want immediate visible text generation. The third is `/chat/stream/sentences`, which buffers tokens server-side and emits complete sentences. Sentence streaming is useful for voice and avatar clients because text-to-speech systems usually perform better when they receive complete sentence-sized chunks instead of raw token fragments.

There is also a persistent WebSocket endpoint at `/api/v1/ws/chat/{session_id}`. It is designed for real-time voice or avatar agents where a client keeps the connection open and sends one JSON message per turn. The server returns metadata, sentence events, and a done event over the same connection. Authentication is handled through a token query parameter because browsers cannot attach normal Authorization headers during the WebSocket handshake. The WebSocket path also validates that the authenticated token user matches the user id in the message payload.

Latency work was treated as a product feature, not an afterthought. The system has several optimizations designed around fast emotional response. Groq is used as the low-latency path when `GROQ_API_KEY` is configured, because it can perform sentiment and generation much faster than the Gemini fallback in this application. The workflow uses the same low-latency service for sentiment and therapy generation when Groq is available. Gemini remains available as a fallback, but the code comments note that Gemini 2.5 Flash can add an 8 to 10 second thinking phase in this path, which is not ideal for conversational latency.

RAG latency was reduced in several ways. Short neutral messages skip retrieval entirely. MMR candidate counts were reduced to keep the retrieval set small. The raw and expanded MMR searches run concurrently with `asyncio.gather` and `asyncio.to_thread`, so blocking vector-store work does not freeze the event loop. Cross-encoder reranking is lazy and opt-in instead of always-on. The RAG service also caches final rendered context by an MD5 key of `query|mood` for 300 seconds. If the same user concern appears again, the system can reuse the context instead of repeating retrieval and reranking. Redis can be injected for a shared production cache, with a local in-process cache as a development fallback.

The latency benchmark suite measures real application behavior rather than mocked unit behavior. The tests require a running server and call the real endpoints, real LLM providers, real RAG retrieval, and real database path. This gives a more honest view of production-path timing. The benchmark suite measures blocking chat for trivial messages, clinical messages, and crisis messages. It also measures cold versus warm RAG cache behavior, three concurrent chat requests, SSE time to first token, SSE time to first sentence, and WebSocket time to first sentence over a persistent connection.

The expected latency budgets are configurable through environment variables. By default, blocking chat should stay under an 8 second median ceiling, crisis response under 3 seconds, time to first token under 4 seconds, and time to first sentence under 6 seconds. These ceilings are intentionally generous because real LLM provider latency varies, especially on free-tier APIs. The tests also include pacing between calls to reduce provider rate-limit backoff, which can otherwise look like an application regression.

The crisis path is especially important for latency and safety. A crisis message still requires sentiment/risk analysis, but once the risk score is high, the response skips RAG and skips generative therapy output. The deterministic crisis template can be returned quickly and consistently. This ensures that the most urgent user state does not wait behind retrieval, reranking, or long-form generation.

Overall, the system was created by combining four layers: a stateful LangGraph conversation brain, a safety-first risk router, a precision-focused clinical RAG pipeline, and latency-aware streaming APIs. The result is a chat feature that can behave like a responsible psychologist-style support assistant: it listens, detects mood, recognizes crisis, remembers context, retrieves evidence, responds gently, and keeps the interaction fast enough for chat, voice, and avatar experiences.
